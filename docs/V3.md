# V3 dynamique locale

Branche `feat/v3-local-dynamic`, créée depuis `experiment/netlify-v3-backend-poc`
au commit exact `72a86db6e935fe28d63f57fcc9a7e31ef9fe6de7` après récupération explicite
sur origin. `main`, le workflow Pages et le comportement V2 restent conservés.
Aucune PR, fusion, création de service ou publication.

## Démarrer et arrêter

Node **24** recommandé (22.19+ pour le moteur), npm et connexion Internet.
À la racine du dépôt :

```sh
npm ci
# Lire d’abord les conditions FOSSGIS ci-dessous ; usage personnel local seulement.
V3_FOSSGIS_POLICY_REVIEWED=true npm run dev:v3
```

Le navigateur local utilise le port **5173**, le backend le port **8787**.
Les deux écoutent exclusivement sur `127.0.0.1`. Ces ports doivent être libres.
Aucune clé, compte Netlify ou backend hébergé n’est nécessaire. Le jeton d’API
est généré en mémoire et injecté par le proxy Vite, jamais envoyé à React.
Dans un environnement cloud il faut un transfert de port distinct ; les adresses
loopback ne constituent pas un aperçu public de l’interface.

Arrêter avec **Ctrl+C**, puis attendre la fermeture. Une opération en cours peut
attendre sa limite de 90 secondes ; annuler dans l’interface avant d’arrêter pour
obtenir un arrêt coopératif. Un arrêt brutal préserve les checkpoints déjà écrits.
Au redémarrage, le dernier job est relu et « Reprendre un calcul interrompu »
redéclenche le runner après expiration de son verrou (jusqu’à 180 secondes).
Un job explicitement annulé reste terminal : relancer une comparaison réutilise
les réponses compatibles du cache, sans ressusciter le job annulé.

L’arrêt anticipé est **désactivé par défaut**. Pour l’activer :

```sh
V3_FOSSGIS_POLICY_REVIEWED=true V3_EARLY_NO_TOLLS=true npm run dev:v3
```

Le désactiver demande simplement de retirer `V3_EARLY_NO_TOLLS=true` puis de
redémarrer. La configuration participe à l’identité de la recherche.
Neuf sondes doivent retourner des ensembles identiques de représentants,
avec toutes les analyses strictes réussies et exactement zéro km exposé.
Cela ne prouve pas un optimum global.

V2 reste accessible via `npm run dev`, `npm run build` et `npm run preview`.
Ne pas lancer V2 et V3 simultanément sur le même port.

## Interface

Fond crème, typographie et vert de la V2 ; grand titre « Votre trajet. Vos
compromis. ». Deux champs IGN avec suggestions détaillées (libellé, commune,
code postal, type), choix explicite à la souris ou au clavier, bouton d’inversion.
Modifier le texte invalide immédiatement la sélection. Aucun premier candidat
n’est choisi silencieusement. Un trajet confirmé au lancement reste affiché
au-dessus des résultats même si l’utilisateur modifie ensuite ses champs.

La progression affiche profils/plafond 40, géométries distinctes et analyses.
L’indicateur représente le budget de profils, pas un temps restant ; la stratégie
peut finir avant 40. Les résultats provisoires apparaissent dès les checkpoints.
Les erreurs de réseau sont reformulées et les traces techniques restent locales.

Cartes de résultats : durée, distance, détour par rapport au plus rapide observé,
km marqués à péage ou analyse en attente, toujours « Tarif non disponible ».
Le filtre de détour agit immédiatement sans recalcul réseau. L’économie minimale
est désactivée tant qu’aucun tarif fiable n’est intégré. Les choix mis en évidence
sont le plus rapide et le moins exposé parmi les compromis admissibles. Aucun score
monétaire ni compromis intermédiaire artificiel. Les résultats partiels restent
explicitement provisoires.

Le graphique accessible au clavier représente détour/min et exposition/km,
avec points synchronisés aux cartes et au tracé Leaflet sélectionné. La carte
recadre chaque géométrie réelle, identifie départ/arrivée et évite les réponses
tardives. Les autres variantes ne sont pas superposées pour préserver la lisibilité.
L’exposition n’est jamais assimilée à un prix.

## Architecture

- `src/v3/` : UI React, port métier `RoutingProvider`, adaptateur HTTP. Aucun détail
  FOSSGIS ni secret dans le frontend. L’ancienne interface V2 demeure sélectionnée
  dans les modes Vite habituels ; le mode `v3` active l’interface dynamique.
- `scripts/dev-v3.mjs` : lance Vite et le backend dans une commande, gère les signaux.
- `server/src/api.mjs` : API métier recherche, géocodage, statut, géométrie,
  annulation, reprise ; contrôle Origin et jeton.
- `server/src/jobs.mjs` : états, leases, checkpoints, progression et résultats
  partiels. Stratégie et déduplication extraites du POC validé, sans console ni
  adaptateur Netlify dans le produit.
- `server/src/providers.mjs` : port routage et adaptateurs FOSSGIS/IGN.
- `server/src/store.mjs` : stockage fichier avec renommage atomique, CAS sérialisé
  dans **un seul processus** ; port remplaçable pour un futur hébergement.
- Le POC et son adaptateur Netlify restent isolés dans `experiments/backend-v3`.
  Le produit ne les importe pas et ne dépend pas du SDK Netlify.

L’optimisation produit est durée/exposition seulement. Le statut tarifaire reste
explicite dans le contrat et permet une future frontière durée/euros lorsque
l’intégration de tarifs fiables sera développée. Les archives APRR ne sont pas
forcées dans cette recherche dynamique.

## Cache, persistance et limites

`.local-v3/` est ignoré par Git : jobs, géométries, réponses et logs réseau.
Les clés comprennent coordonnées exactes orientées, options, fournisseur,
version de stratégie et graphe Valhalla, avec option d’arrêt anticipé pour le job.
Avant de restituer un résultat terminé du cache, le moteur recontrôle le graphe
sur `/status` ; aucun nouvel appel route/trace n’est nécessaire en cache chaud.
Il recontrôle aussi le graphe au début et à la fin d’un calcul. Un changement
invalide le succès au lieu d’afficher un résultat d’un autre graphe. Les appels
concurrents de contrôle sont regroupés ; pendant une campagne active, son graphe
observé peut être réutilisé jusqu’à cinq minutes avant les contrôles du runner.

Résultats/réponses valides 24 h ; géocodage positif 24 h, négatif 1 minute.
« Résultat récupéré depuis le cache » apparaît uniquement pour un job terminé
réellement réutilisé. Les archives de recherche ne sont jamais préchargées dans
le cache produit.

Annulation coopérative : l’appel déjà engagé finit ou expire, puis aucun nouveau
routage n’est lancé. Une panne entre réponse et écriture peut causer un appel
répété après reprise. Le système ne promet pas exactement une requête par profil.
Une seule campagne fournisseur active ; les autres reçoivent un message d’attente.
Budget interne 8 minutes, timeout amont 90 secondes ; échec ou timeout ne deviennent
jamais un faux résultat complet. Les checkpoints compatibles sont réutilisables.

Pas de purge physique automatique : après arrêt de l’application, supprimer
`.local-v3/` si l’on souhaite effacer les adresses, traces et caches locaux. Le
navigateur conserve seulement identifiant du dernier job et libellés dans
`v3-job` / `v3-labels`, effaçables via ses données du site. Aucun de ces fichiers
ou valeurs ne doit être commité. Ne pas partager le serveur local sur Internet.

## Conditions et réseau

Usage personnel uniquement, pas d’offre publique utilisant FOSSGIS sans réévaluation.
Conditions : https://www.fossgis.de/arbeitsgruppen/osm-server/nutzungsbedingungen/
Une seule campagne, appels séquentiels, délai de **2 secondes après chaque
réponse**, identification User-Agent et Referer, pas de contournement d’un refus
ni relance automatique des erreurs amont. L’attribution OSM et le lien de
signalement sont visibles. Les tuiles OSM sont indépendantes des serveurs FOSSGIS.

Destinations nécessaires : `data.geopf.fr`, `valhalla1.openstreetmap.de`,
`tile.openstreetmap.org` ; `www.fossgis.de` pour consulter les conditions.
Les autorisations ont été ajoutées au brouillon de l’environnement Codex ; leur
sauvegarde n’applique pas à elle seule les changements dans la machine courante.
Les paramètres réseau de l’environnement doivent être appliqués avant un nouvel
essai réel. Aucun déploiement applicatif n’est nécessaire.

nombre de routes ni changement de graphe n’a été constaté ; il serait incorrect
d’attribuer une différence au graphe actuel.

**Rennes → Saint-Brieuc :** nouvel essai réel avec arrêt anticipé activé, même
blocage avant calcul. Le test automatisé valide les neuf sondes identiques,
l’analyse stricte et l’arrêt à zéro ; la campagne réelle actuelle reste à faire.
Les données de l’ancien POC ne sont pas présentées comme une validation de V3.

Commandes de validation depuis la racine :

```sh

npm run test:e2e:v3
# Après rétablissement du réseau, séquentiellement :

```

Le script réel sauvegarde mesures, observations et erreurs dans `.local-v3/`,
vérifie la réutilisation chaude sans route/trace et compare les hashes Crans
aux géométries historiques. Les différences exigent une investigation explicite,
pas une justification automatique par un changement de graphe.

Avant une V3 publiable : réussir les campagnes réelles et les essais navigateur
avec géocodage/tuiles réels, choisir un fournisseur autorisant l’usage prévu,
préparer authentification publique, contrôle d’abus, stockage distribué/purge,
politique de conservation des adresses, supervision et garanties de reprise du
runtime choisi. La tarification fiable est un chantier distinct. Aucun compte,
service hébergé ou déploiement n’a été créé pour cette étape.
